## Provisional decisions (taken, reversible)
- The erase event payload is `path_hash` (sha256 of each relative path), `versions` (snapshot ids) and `reason`. It does not store the path or the file bytes.
- Objects are deleted before the event is appended, so a search rebuild cannot read them. Manifests stay, so the version id in older events still resolves. `history()` hides those ids. `file_at` returns nothing when the object is gone.
- An object shared with a version that was not erased is kept.
- Blobs under `.iterthink/blobs/` are deleted only when every event that names them also names an erased version. The events stay.
- The current working file is left as it is. Erase removes history, not the file on disk. A later snapshot can store those bytes again.
- Another machine drops the bytes the next time it reads history or a version. `apply_erases` does that. Nothing in the disk watcher calls it yet.
- The page is two steps: Review, then Erase. The first step does not delete.

## Proposed Erase section
The spec has no Erase section. Audit trail says logs are never rewritten. This slice follows that. Proposed text for `docs/spec/audit-and-security.md`:

```
# Erase
- Personal data or a wrong upload can be erased from history. Snapshot objects
  that only the erased versions referenced are deleted. Blobs referenced only
  by events that name those versions are deleted too.
- The log is not rewritten. A new erase event records a hash of each file
  path, the version ids, who erased, and the reason. It does not record the
  content or the path.
- Erase needs a reason and a second confirmation.
- Another machine drops the same bytes the next time it reads history.
- Checkpoints and handover bundles made before the erase still verify. The
  chain is unchanged. A bundle made before the erase still contains what it
  contained then.
```
